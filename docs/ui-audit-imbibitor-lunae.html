Reading the waterline

Six Audit Currents

The matrix is not a random polish list. It separates engineering hygiene from product direction so each PR can stay narrow, reviewable, and provable.

A11y semantics

Several controls look clickable but are not native controls, or they use visual state without accessible names. This is the clean first fix.

Toolbar overload

Headers, rails, sidebars, and editors expose too many same-weight icon actions. This needs design and product hierarchy work, so it waits.

Risky actions

Delete, undo, reset, retry, and force actions often hide their consequence. These need confirmation policy and clearer labels.

Primary path clarity

Some surfaces mix setup, context, generation, save, and launch actions in the same moment. That is a design problem, not a quick ARIA pass.

Modal and sheet behavior

Overlays use inconsistent dialog semantics, close names, Escape behavior, and focus return. Some fixes are simple, others depend on shared primitives.

Vocabulary and state

Labels like Browser, Encounter, Delete more, Connection, and visual_novel create avoidable confusion. Some can be renamed now, some need ownership decisions.

Order of Work

The work should move like a clean five-step current. Start with the small semantic win, open decision issues, then return to destructive flows and bigger hierarchy work.

2

Pick PR 1: A11y Semantics

Start with rows where the audit says: can fix now, no product decision, and proof is cheap. The first PR is native controls, keyboard activation, accessible names, and ARIA state.

3

Open decision issues

Do not code product decisions yet. Write short issues for toolbar grouping, mobile menu hierarchy, destructive policy, editor priority, visual_novel ownership, and the settings drawer direction.

4

Then PR 2: Risky Actions

After PR 1 lands, improve the bulk delete and selection flows: rename Delete more, show selected range or count, add confirmation, and clarify destructive labels.

5

Use Impeccable later

Bring design critique into hierarchy PRs: conversation toolbar regrouping, roleplay compact menu, game action rail, and settings drawer preset management. PR 1 is engineering hygiene.

First edict

PR 1: Semantics Only

The next command should be narrow: implement PR 1 from docs/ui-audits.md, A11y semantics only. Keep behavior and hierarchy stable.

Do this

  • Convert Home quick-start cards to real button type="button" controls.
  • Fix chat and sidebar row keyboard activation or convert primary row actions to native buttons.
  • Add missing aria-label, aria-expanded, aria-controls, and active state labels where the audit already calls them out.
  • Expose selected states on tabs and icon controls without changing what they do.
  • Run a keyboard-only pass through Home and the chat list.

Do not do this

  • Do not regroup toolbars or move actions into menus.
  • Do not redesign mobile hierarchy.
  • Do not change destructive action policy yet.
  • Do not rename broad product concepts unless the audit marks them as low-risk labels.
  • Do not touch chat, roleplay, and game ownership boundaries at the same time.
Proof rite

How to Prove It

PR 1 is easy to prove because it does not ask whether the product should work differently. It asks whether existing actions can be reached and named.

Manual checks

  • Tab through Home, start cards, recent chats, sidebar tabs, and chat rows.
  • Use Enter and Space on each primary action.
  • Confirm focus is visible and does not resize the layout.
  • Inspect accessible names for icon-only controls that were touched.

Repo checks

  • Run pnpm typecheck for TypeScript and React changes.
  • Run pnpm check:architecture if imports or boundaries change.
  • Run pnpm check:docs if the PR updates docs or agent guidance.
  • Use browser proof for keyboard behavior where feasible.

Sealed questions

Decisions Before Design

These rows should become short decision issues or doc notes. The goal is to make the future PRs smaller, not to solve every product question in the first PR.

Toolbar grouping strategy

Which actions stay visible, and which belong in Context, Manage, Media, or More?

Mobile menu hierarchy

Should mobile show labeled rows, grouped sections, or direct icon access?

Destructive policy

When should Marinara confirm, undo, or allow one-click removal?

Editor priority

Are catalog editors mainly edit surfaces, or launch and use surfaces?

visual_novel ownership

Is visual_novel a supported mode, a roleplay variant, or legacy naming?

Settings drawer direction

Is it a quick setup panel, an expert console, or both with progressive disclosure?
